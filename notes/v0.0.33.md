# v0.0.33 - sessions you can see and end, seven-day sliding window

The last open "Medium" item of the security review closes with this
release (audit finding F4, see Audit.md in the repository): cookies
lived for 30 days and there was no way to see - let alone end - the
sessions an account holds.

## What changed

- **Seven days by default, sliding.** `FXCLOUD_SESSION_TTL` still
  overrides the window in seconds; the default drops from 30 days
  (2592000) to 7 days (604800). A session in use no longer dies under
  its user: any API request carrying the cookie renews the window to
  seven days from that call. The renewal is written at most once per
  window (a quarter of the lifetime, capped at a day), so an in-use
  session costs one indexed statement that matches nothing and the
  hot path never turns into a stream of writes.
- **A session list in the settings dialog**, below the password
  section: every live session with the device it was created on (the
  User-Agent captured at sign-in), when it was created, when it was
  last used and when it expires. The row belonging to this browser is
  marked "this device". Each other row has an End button behind a
  confirmation, and one button ends *every* other session at once -
  "sign out everywhere else", the incident case.
- **Three new endpoints** for the same thing over the API:
  `GET /api/me/sessions` (handles and timestamps, never the token),
  `DELETE /api/me/sessions` (ends all but the caller, answers
  `{ended: n}`) and `DELETE /api/me/sessions/{sid}` (ends one;
  another account's sid is 404, never a hint that it exists).
- **Migration 013** adds the bookkeeping to existing databases: a
  public `sid` handle per session (random 16 bytes), the `user_agent`
  line (empty for sessions created before this release - they show no
  device) and `last_seen_at` (backfilled to the creation time).

## Why it matters

Before this release a session cookie that leaked - a copied cookie
jar, a proxy log, a browser extension reading the jar - stayed valid
for up to 30 days, and the only answer an operator had was "change
the password and hope", which has in fact worked only since v0.0.31
began ending sibling sessions on a password change. Now the account
holder can look at the list, recognise the strange device by its user
agent and end it on the spot, or end everything else with one click;
and an idle session dies by itself within a week.

## Trade-offs, stated openly

- Renewal slides the expiry but does **not** rotate the token value:
  a second open tab holds the old value and would get a 401
  mid-renewal, bouncing that tab's user back to the login page. A
  cookie a thief is actively using therefore stays usable while it is
  used - the countermeasure is the list itself, which names the
  device and offers the end button.
- The `sid` in the listing is a label, not a key: it carries no
  power, every query using it is scoped to the caller's own sessions,
  and a session's real identifier never leaves the HttpOnly cookie.

## Action required

- Operators: none; migration 013 runs on startup. If you had raised
  `FXCLOUD_SESSION_TTL` deliberately, note that renewal now keeps an
  active session alive for that whole window (an idle one still
  expires after it, as before).
- Users: existing sessions keep their old expiry until they are next
  used; from that call on they live seven days (or your configured
  window) and slide from there.
