# v0.0.34 - the audit's small hardening items: capped walks, an origin warning, login timing parity

This release closes the last open work line of the security review
(Audit.md in the repository): three findings that each deserved a fix
but not a release of their own ride together. F1 to F8 and F10 are
done; what remains in the audit are accepted trade-offs, written down
on purpose.

## What changed

- **Depth caps on the parent walks (F6).** Two places climb a folder's
  parent chain: one already capped the walk at 64 hops and turned a
  corrupt cycle into a clean 404; the share-covering walk and the
  breadcrumb walk did not, and a corrupted database could have made
  them spin a connection thread forever instead of answering. Both
  now stop at the same 64 hops - the share walk answers "no share",
  the breadcrumb walk a 404 - and folders deeper than 64 were
  unreachable anyway. Nothing reachable through the API changes: the
  editor refuses to build a cycle in the first place; this is the
  robustness net under the net.
- **A startup warning for the derived passkey origin (F8).** Without
  `FXCLOUD_ORIGIN` fxcloud derives the WebAuthn origin from the
  request's `Host` - fine for `http://127.0.0.1` development, a
  silent trap behind a reverse proxy that rewrites `Host`: passkeys
  would stop working without an error anyone sees. Startup now logs a
  WARN naming the bind address whenever it listens beyond loopback
  without the knob. The dev server stays quiet; setting the knob
  silences it anywhere.
- **Login timing parity (F10).** An unknown username used to answer
  401 in milliseconds while a wrong password paid a full Argon2
  verification - stopwatch enumeration of account names. The
  unknown-name path now spends the same verification against a fixed
  dummy hash, so both cost ~180 ms and the two 401s are byte-identical.
  The spend is bounded exactly like every other failed sign-in: the
  per-address budget from v0.0.30 refuses further attempts with 429.

## Why it matters

None of these is an exploit path today - the audit says so in each
finding - and all three are the cheap insurance you want before you
notice the bill: a corrupted database page costs a restart instead of
an outage; a proxy migration announces itself in the journal instead
of in a support ticket; and an attacker enumerating names gets noise
where there used to be a stopwatch.

## Trade-offs, stated openly

- The timing fix makes every unknown-name attempt as expensive as a
  wrong password - by design; that is what equalizes them. The rate
  limiter is what bounds the cost, which is why the two fixes ship as
  a pair.
- The dummy hash is a constant in the source: someone with repository
  access can tell a dummy verification from a real one by the hash
  string, not by timing. The threat model this finding addresses
  (timing over HTTP) cannot see the difference.
- The passkey challenge door still saves one database read for unknown
  names (sub-millisecond, already behind the same account backoff);
  documented in Audit.md as remaining by design.

## Action required

- Operators: none. If you run fxcloud beyond loopback without
  `FXCLOUD_ORIGIN` and see the new WARN, that is the finding, not a
  regression: set the knob to the URL users open fxcloud under.
- This is also the first release whose installer verifies the download
  against the `SHA256SUMS` asset the release now carries (F7, shipped
  without a version bump right after v0.0.33) - the update line
  reports "checksum verified against SHA256SUMS".
