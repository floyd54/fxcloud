# v0.2.2 - auto-unlock: open without the passphrase

The last piece of phase 4, and a DECISION 7 promise: unlock
persistence. With the storage passphrase defaulting to the login
password (DECISION 3), the expected behaviour is that fxcloud simply
*opens* encrypted - and now it does, behind an explicit switch: a
device that has unlocked once keeps opening the account without
asking again. The passphrase is asked for exactly one moment: the
explicit badge switch from Unencrypted to Encrypted inside a live tab.

## What changed

- **The switch** (`users.auto_unlock`, migration 021): stored with the
  account, returned by `GET /api/me`, saved through the same partial
  `PUT /api/me` as every other setting (a non-boolean answers422, an
  empty body still400). New accounts default to off - nobody
  auto-unlocks before the owner has seen the switch.
- **The device blob.** After a real unlock (pane or sign-in handoff) the
  browser stores `{deviceKey, wrappedArk}` in
  `localStorage["fxcloud.device_unlock.<user_id>"]` - a random device
  key and the ARK wrapped under it. **The password itself is never
  stored.** Init tries the blob before the handoff, so load, reload,
  sign-in (password or passkey) and new tabs on that device open without
  a prompt; the handoff stays as it was for the first login on a fresh
  device. A missing, stale or tampered blob never prompts by itself -
  the pane remains the fallback. Turning the switch off deletes the blob
  and returns to exactly the v1 behaviour: memory-only keys per tab.
- **Honest about the trade.** Whoever can read this browser profile
  wholesale gets this account's keys on this device - which is why the
  switch is off by default and why ENCRYPTION.md section 11 names the
  exception. What is never exposed is the login password itself, which a
  parked-password scheme would have traded away instead.
- **Docs.** ENCRYPTION.md: the DECISION 7 prose and its summary row are
  rewritten (device keys are no longer "future work"), section 5.7
  gains the switch paragraph and the prompt matrix, sections 5.6 and 11
  name both localStorage residents, and both code headers match the
  code. USERGUIDE section 11 documents Auto-unlock in user language,
  trade-off included.

## Compatibility

Additive: one pragma-guarded column with default 0, one boolean in the
partial settings update, one localStorage key the server never sees. No
endpoint, format or session change. An instance whose migration has not
run simply has no switch (the UI reads the field off `GET /api/me`),
and an account with the switch off behaves byte-for-byte like v0.2.1.

## Tests

The suite grew by5 checks to **824** (flag roundtrip over `PUT /api/me`
and the DB, non-boolean refused with422, empty body still400). The
crypto roundtrip gained the device-blob pair (wrap and open the ARK,
foreign device key refused) and the `sessionFromArk` reconstruction
(root key and public blob identical to the passphrase path).
fxenc-harness now models localStorage - its own rule: anything the code
asks for and the harness does not model throws rather than vanishing.
`cargo test` stays at73. Every gate (fmt, clippy with warnings denied,
qjsc, call arity, i18n parity across de/en/tlh) runs before the tests
on every push.
