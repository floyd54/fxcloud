# v0.0.30 - only the row's owner replaces an existing key record

A share grantee can no longer swap out a stored key wrapper, closing
audit finding F5 (see Audit.md in the repository).

## What changed

- `PUT /api/files/key` now draws exactly the line the content save
  already draws: a key record that *exists* may only be replaced by
  the row's owner. A row with *no* record can still be given one by
  anyone holding UPDATE - the first encrypted write below a shared
  folder, which is the documented purpose of that door.
- The refusal names its reason ("only the row's owner may change its
  key record") instead of a bare 403.

## Why it matters

The server never sees encryption keys, so confidentiality was never at
risk - but a grantee with UPDATE could have replaced the wrapper with
one only they can unwrap. The owner would then be unable to open every
*future* write in that tree, an availability hit that survives
restarts and stays invisible until the next encrypted save.

## Trade-off, stated openly

An UPDATE-grantee can no longer re-bind an encrypted row that was
moved inside a share. There is no condition under which such a
replacement is verifiably benign, so the frontend refuses that
transfer up front - before the re-bind half runs - names the reason,
and leaves the row where it was rather than delivering it unopenable.
The owner moves it instead.

## Action required

None. Owners are unaffected; grantees lose one obscure move path.
