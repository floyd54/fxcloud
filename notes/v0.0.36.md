# v0.0.36 - the language menu is readable in light mode again

A small release for one visible defect, reported from daily use: **in the
light theme, the texts of the language selection could not be read.** The
language switcher is a single button showing the current flag; it opens a
menu with the language names (English, Deutsch, tlhIngan Hol). In light
mode those names were white on a white menu - invisible. This is a
user-interface fix and carries no server or data changes.

## What the bug was

The language menu lives in three places: the top bar, the settings dialog
and the login card. Only the **top bar** host was affected, and the cause
is a CSS specificity trap with history:

- The top bar is permanently blue and paints every button inside it white:
  `.topbar button { color: #fff; ... }`. That rule is more specific than
  the menu rows' own `.lang-btn { color: inherit; ... }`, so inside the
  top bar DOM the rows received white text.
- The menu panel itself is themed: `background: var(--panel)` - white in
  light mode, dark panel in dark mode. White text on that white panel is
  the unreadable combination; in dark mode white-on-dark happens to be
  readable, which is why the defect only ever showed in the light theme.
- This failure class was met before: the user dropdown sits in the same
  spot, and the stylesheet carries a comment explaining that it needed a
  `.topbar` prefix for exactly this reason ("white text onto the white
  panel and be invisible in light mode"). The language rows never got
  that prefix.

## What changed

- `.topbar .lang-btn` now restates the row's own values - text color from
  the theme, the row's padding, radius and font size, and a transparent
  background - so it outranks the top bar's blanket button rule in both
  themes.
- Hover and active states are restated next to it. The new equally
  specific block would otherwise out-rank the unprefixed hover rule and
  silently kill the row feedback - a fix that breaks two things at once
  is not a fix.
- The settings dialog and the login card hosts are outside the top bar
  DOM, were never affected, and are untouched. The trigger button itself
  shows only the flag (opaque SVG colors) and needed no change.

## Why it matters

The language picker is the first door a non-English speaker walks
through, and in the default (light) theme it was a blank white menu.
Defects that hide a whole control count double: the feature looks
present but is unusable.

## Trade-offs, stated openly

- The fix is one more `.topbar`-prefixed block, i.e. one more place where
  a top bar override must be kept in step with the base rule. The
  alternative - restructure the top bar so it stops styling descendant
  buttons - would touch every button in the header for a bug that has a
  two-line, precedented remedy.
- Two suite pins now guard the block and its restated hover/active
  states (556 checks total), so the specificity trap cannot be
  "simplified" back into the code unnoticed.

## Action required

- Operators: none; the change ships inside the binary's embedded
  frontend.
- Users: hard-refresh the page (Ctrl+Shift+R) once after the update if
  the language menu still looks white-on-white - the browser may hold
  the previous stylesheet.
