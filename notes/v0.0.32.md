# v0.0.32 - rate limiting on every sign-in door

Every authentication endpoint now counts its attempts and answers a
flood with 429 + `Retry-After`, closing audit finding F1 (see
Audit.md in the repository).

## What changed

- **Per-account lockout with exponential backoff.** Five consecutive
  wrong passwords on one name buy a 10-second window; every further
  attempt doubles it, up to five minutes. The refusal happens *before*
  the database or the password hash see the request, so a locked name
  costs the server nothing - and the right password waits out the
  window too, which is what keeps the refusal cheap. One successful
  sign-in clears the counter.
- **No enumeration through the 429.** The counter is keyed by the
  name itself, existing or not: an invented name locks exactly like a
  real one, so the response never tells an attacker who has an account.
- **Per-source budgets.** One address may spend 30 failed sign-ins per
  minute and 10 registrations per ten minutes; both answer with 429
  and `Retry-After`, the register budget *before* its password hash
  runs. The key is the socket peer address only - `X-Forwarded-For` is
  deliberately never trusted, because a bare install would be one
  spoofed header away from a limiter that both misses the attacker and
  can be aimed at other users. Behind a reverse proxy these budgets
  therefore describe the proxy's address, where they are set
  generously on purpose: the per-account lockout stays the precise
  instrument.
- **WebAuthn challenge cap.** At most 256 pending challenges; beyond
  that the passkey start endpoints refuse with 429 instead of the map
  growing with the flood.
- **The UI translates the wait.** `rate_limited` answers arrive with
  the number of seconds in the body next to the `Retry-After` header,
  and the login page counts in your language.

## Action required

None for humans. Automated scripts hammering the login API will now
see 429s; a person who mistypes their password five times in a row
waits a few seconds - by design. If your install sits behind a reverse
proxy, note that the source budgets count the proxy's address: with a
shared budget of 30 failed sign-ins per minute, a distributed attack
is throttled at the account level while the shared budget only caps
the aggregate.
