# v0.1.2 - every content replacement keeps a restorable version

The second of the three planned work lines (`concepts/versioning.md`),
and the first with a new button to click: **a wrong save is no longer
the end of a file**. The editor save and every WebDAV `PUT` now keep the
replaced bytes as a version, and the file's row menu opens its history -
download any version, restore it, undo the restore the same way. The
dialog appears in your language (en/de/tlh), and two bounds in
**Settings > Version history** keep a long-lived file from growing a
history nobody wants.

## What changed

- **The editor's Save and a WebDAV PUT keep the outgoing bytes** under
  their own name (`blobs/_versions/<file>/<key>`), written with the
  same link-then-row discipline as everything else: a crash between the
  two leaves one orphan file, never a row pointing at nothing. Saving
  an empty file for the first time keeps no empty history. Uploads stay
  create-only, so versioning starts with the first *save* of a file.
- **Version history in the row menu**: newest first, with time and
  size, plus per version **Download** (byte ranges work on versions
  like on the current file), **Restore** and **Delete**. Restore is an
  exchange - the chosen version becomes the content and what was
  current becomes the newest version - so it is itself undoable. A
  read-only share sees the history and can download versions;
  restoring or deleting needs write permission.
- **Two retention bounds in Settings** ("Version history"): how many
  versions to keep per file, and an age in days - `0` disables either
  bound. The count is applied whenever a version is saved, the age by
  the background sweep that already runs the trash purge. Defaults
  keep 20 versions up to 180 days.
- **History counts against your quota** (`used_bytes` includes the
  kept versions of your live files, the admin list shows the two sums
  apart), the **trash keeps a file's history** until the file is
  purged, and the purge removes the version rows and their bytes along
  with everything else.
- Four new endpoints behind the usual gates: `GET
  /api/files/versions`, `GET /api/files/version/download` (ranged like
  the entry download, with the type the version had when it was
  saved), `POST /api/files/version/restore`, `DELETE
  /api/files/version`.

## Compatibility

Self-applying: three migrations add `file_versions` and the two user
columns on startup, so restarting the new binary is the whole upgrade.
No API and no client change beyond the dialog - a browser sitting on
an open session needs no hard reload, only the usual binary restart.
Files stored before this release simply have no history yet; their
first save starts it.

## Tests

The suite grew by 42 checks to **622**: the history walked end to end
(two saves keep the first bytes, byte-exact and ranged version
downloads, the undoable exchange, the READ-grantee boundary, delete
dropping the bytes from disk, the zero-byte skip of a first fill), the
settings round-trip and its 400, retention by count and by age with
the pruned blobs verified gone from disk, the quota sum across live
rows and history, and the trash/purge lifecycle including every
version blob. The unit tests grew by five to **48** (both retention
bounds, the quota sums, the restore exchange).
