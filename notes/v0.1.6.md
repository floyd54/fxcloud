# v0.1.6 - the admin dialog learns a sidebar

A polish release with no server changes: the user administration took
the settings dialog's nav-plus-panes shape. Three accounts and a
handful of groups stacked the two sections into one column that
outgrew the viewport - the close button sat below the fold and the
dialog had to be scrolled blind to reach it. The dialog now opens on
a **Users** tab with the account table, the **Group folders** tab
beside it holds the group list and the create row, and the footer
with Close stays pinned at the bottom at any row count.

## What changed

- **Two tabs, one screen.** The dialog reuses the settings dialog's
  nav column and panes (`settings-layout`), so both dialogs share one
  look and one behaviour: the content column scrolls, the tab row
  stays put, and a narrow screen gets the same horizontal nav row the
  settings dialog already had. The dialog always reopens on Users.
- **Nothing else moved.** The account table, the status line, the
  group cards and the create row keep their ids and their behaviour -
  activation, role toggles, quota and password reset on one tab,
  group CRUD with the quota-against-consumption view on the other.
  The settings dialog only became more robust: its tab code is now
  scoped to its own dialog, which the admin dialog's borrowed
  classes would otherwise have tripped.

## Compatibility

Frontend only: no migration, no API change, no configuration. A hard
reload picks the new dialog up; every open session keeps working.

## Tests

The suite grew by 2 checks to **757**: the admin dialog must carry
the tab structure (nav plus panes) and the app.js wiring must switch
panes and reopen on Users. Everything else is untouched - the full
run stays green.
