# v0.2.1 - migrate, zone, recover (encryption phase 4)

Phase 4 of the client-side encryption, and the three questions
ENCRYPTION.md left open for it: the files that already exist get
encrypted ("Encrypt existing files"), the blanket badge gets a
per-folder exception (the write zone), and the recovery key stops being
a value that is shown exactly once - it can be shown again while the
passphrase is known, and reissued with one confirmation. The design,
the reasoning and the three decisions are in ENCRYPTION.md sections 10,
12 and 13 (rows 13-15).

Alongside it the office-installer polish of the days after v0.2.0: the
one-liner asks for the office hostname on a terminal, prints the
engine's published port the moment the container comes up (the number a
reverse proxy needs - no `ss` digging), seeds a landing page that links
to `FXCLOUD_ORIGIN`, and repairs the nginx location that made exactly
that landing page answer 500.

## What changed

- **Migrate: "Encrypt existing files"** (Settings > Account, or
  "Encrypt folder now..." in a folder's row menu). A client-side batch
  job walks the tree, downloads each plaintext row, mints and wraps its
  key under the folder chain, encrypts in the worker and promotes the
  row with `enc=1&key=&history=drop`. The flag is the destructive half
  on purpose: the plaintext version history a normal save would pin is
  exactly the plaintext the encryption removes - the migration save
  skips the pin and deletes that row's versions (rows and blobs go
  together, under the save's write lock), and the quota gate charges
  only the net growth. The dialog shows `i of n`, cancels between rows,
  resumes by rerunning (an encrypted row is counted, never touched) and
  pauses on a full quota with the server's own message plus "Continue
  after freeing space".
- **The write zone.** A folder marked from its row menu (owner or group
  manager; `PUT /api/files/zone`, a file answers 400, an UPDATE
  grantee403) demands the key for new writes below it even when the
  badge says "Unencrypted": `newFile` refuses before the row exists, an
  upload drop unlocks once, and a plaintext save in the zone is
  promoted - with its plaintext history dropped. The flag rides the
  breadcrumb, so every descendant inherits it; unflagged paths keep
  following the badge alone (DECISION 11 unchanged), and a copy starts
  unflagged. WebDAV stays as it was - the zone is read by the client,
  the server only stores the flag.
- **The recovery key on demand.** Setup stores a second copy of the key
  wrapped under the passphrase KEK (`user_keys.wrapped_recovery`,
  nullable). That adds no new power - a passphrase holder could already
  unwrap the ARK - it only makes the once-shown value retrievable from
  the secret the user still has. Settings > Account shows the key again
  or issues a new one behind a confirmation: the passphrase opens the
  ARK, the new key is wrapped both ways, and `PUT /api/keys/recovery`
  stores both envelopes in one O(1) step - the old key stops working
  with that request (empty envelopes answer400, an account without
  encryption409). Rows set up before this release answer "issue a new
  key"; their first reissue enables showing for them too. The recovery
  file and the setup pane no longer claim the key is "shown once and
  never stored".
- **The installer asks, prints and repairs.** The office hostname comes
  from an interactive prompt on a real terminal (Enter skips), the
  unit's office lines are rerun-proof, and the engine's published port
  is printed in full right after the container starts and again in the
  summary. The seeded `ds-branding.conf` carries a `no-cache` location
  for `/welcome/`, extended in place on existing installs (the conf is
  a single-file bind mount, so install.sh never renames it) and verified
  with a `200` after the reload; the broken `location = /welcome/`
  variant that made nginx answer 500 per request (index module,
  `ENOTDIR`) is replaced automatically on the next run.
- **CI gates.** `cargo fmt --check` and `cargo clippy -- -D warnings`
  now run before the tests: the fmt sweep (45 spots), the clippy pass
  (dead code removed, three lint families allowed where the item
  justifies them) landed with them.

## Compatibility

Additive by construction: `019_enc_zone` (pragma-guarded column,
default 0) and `020_wrapped_recovery` (pragma-guarded, nullable)
upgrade every existing database in place, and nothing reads either
until it is set. `history=drop` exists only behind an explicit flag on
an explicit `enc=1` write - a plain save pins its history exactly as
before, the WOPI save explicitly never sends it, and public links,
WebDAV and the share flow are untouched (the zone flag is stored, never
acted on server-side). Accounts without encryption see the new Settings
entries; pressing one opens the setup flow, like every other
encryption entry.

## Tests

The suite grew by 24 checks to **819**, `cargo test` by 2 to **73**.
New black boxes: the migration save leaving no version row, no blob on
disk and a `404` for the dropped id (plus the two400 refusals), the
zone roundtrip over `info` and `breadcrumb` with `400` for a file and
`403` for an UPDATE grantee, and the recovery NULL-for-old-clients
shape plus the rotation roundtrip with its400. Every push runs the new
gates before the tests: rustfmt, clippy with warnings denied, then
`cargo test`, the integration suite and the image build.
