# v0.1.0 - every content path streams, and downloads answer byte ranges

The first of the three planned work lines (see `concepts/`), and the
only one with no new button to click: **the server now moves file bytes
in chunks instead of buffers**, so what a request costs in memory stops
growing with the file it touches. Nothing about the UI changed - a
browser sitting on an open session needs no hard reload, only the usual
binary restart.

## What changed

- **Upload, editor save and WebDAV PUT stream into a temp file**
  (`data_dir/tmp/...part`) and publish the bytes with a single rename
  once the metadata row exists. A 4 GiB upload costs 64 KiB of RAM;
  before it cost 4 GiB, and on WebDAV twice that, because the body was
  buffered and then copied again.
- **Downloads, previews and WebDAV GET read in 64 KiB chunks** from an
  open file handle instead of handing over a whole-file buffer, so a
  4 GiB download costs the same memory as a 4 KiB one and a client
  that hangs up just has its reader dropped.
- **`GET /api/files/download` now honours byte ranges** exactly like
  the preview already did: `Accept-Ranges: bytes`, `206` with
  `Content-Range` for a slice, `416` with `bytes */len` outside the
  file - a player or `curl -r` can seek without pulling the whole file.
  Both routes go through one range helper, so they cannot drift.
- **A too-large file is refused with `413 payload_too_large` while it
  is counted**, not after it was read: the per-file limit (and
  WebDAV's 4 GiB cap) are numbers the chunk loop checks on every
  piece, and a refused upload's temp file is removed on the spot. The
  request body limit keeps 64 KiB of multipart framing headroom, so
  the counted cap is what refuses the file itself.
- **ZIP downloads stay flat in memory.** The zip crate must seek - its
  headers and the central directory demand it - so a pipe was never
  possible: the archive is built into a temp file on the blocking
  pool, reopened, unlinked immediately and streamed out with its
  length taken from metadata. One temporary file on disk, never the
  archive in RAM, and a crash mid-build is swept at the next startup.
- **The MIME sniffer decides on the first 64 KiB** (ISO magic needs 32
  KiB; the text heuristic windows further to 8 KiB) instead of on the
  whole body. Type detection changes only for files whose earlier
  verdict came from bytes beyond that head.
- Failed writes pair up: the metadata row is rolled back and the temp
  file goes with it; WebDAV COPY copies at the filesystem level; the
  startup sweep removes abandoned temp files.

## Compatibility

Server-side only: same routes, same headers, same status codes except
the new 413, no schema change, no client change. **No hard reload is
needed** - restart the binary as usual (see `install.sh`), and files
already stored read exactly as before.

## Tests

The suite grew by 24 checks to **580**: source pins against the buffer
paths coming back, range answers on `/download`, a 16 MiB round trip
compared byte for byte at its far end, temp-file hygiene after a
success and after a refusal, and a `413` from a sidecar instance
capped at 1 MiB - the cap answers by counting, not by holding. The
unit tests stay at 43.
