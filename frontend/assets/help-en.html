fxcloud User Guide

This guide is for people who *use* an fxcloud instance: how to sign up, work with your files, share them, encrypt them and sign in with a passkey. It also walks an administrator through the one deployment step passkeys care about (HTTPS behind a reverse proxy with FXCLOUD_ORIGIN).

Developer-facing documents:

  • API.md - HTTP endpoints and protocol details
  • ENCRYPTION.md - the cryptographic design in full
  • ARCHITECTURE.md - code layout, storage, quotas

1. Install

fxcloud is a single binary: SQLite and the web interface are built in, there is no database server and no runtime dependency.

One line - installs fxcloud as a systemd service on any Linux with curl (as root); running the same line again updates it:

curl -fsSL https://raw.githubusercontent.com/floyd54/fxcloud/main/install.sh | sh

Prebuilt binary - every tagged release on GitHub Releases ships a fully static Linux x86_64 build (~6 MB):

chmod +x fxcloud-<tag>-x86_64-unknown-linux-musl
FXCLOUD_DATA=/srv/fxcloud ./fxcloud-<tag>-x86_64-unknown-linux-musl

From source:

cargo build --release
./target/release/fxcloud      # creates ./data with the DB and file blobs

Open <http://127.0.0.1:8080>. To run it as a service on Linux, use the hardened unit from deploy/fxcloud.service - the INSTALL.md has the step-by-step. All settings are environment variables (bind address, port, data directory, quota-related limits, ...); the full table is in INSTALL.md.

2. The first account

On a fresh instance, open the Create account tab, pick a username (3 characters or more), an optional display name and a password (8 characters or more).

The first account created on an instance is activated immediately and becomes its administrator. Every account created after that starts inactive: registration succeeds, but sign-in is refused with a hint to contact the administrator until an active account activates it (see User administration).

3. Signing in

The sign-in page has three tabs:

  • Sign in - username and password.
  • Passkey - username only; the device then asks for a PIN or

biometrics (see Passkeys).

  • Create account - registration, as above.

Sessions last 7 days by default (FXCLOUD_SESSION_TTL, sliding while in use).

Install as an app

fxcloud installs like any other web app: in Chrome/Edge use Install app in the address bar, on iPhone/iPad Safari use Share > Add to Home Screen, on Android Chrome the menu > Add to home screen. The app then opens from its own icon in a window without browser chrome - same account, same session, nothing to configure.

Two honest notes: the install is just a launcher (there is no offline mode - fxcloud is a client of your server), and the service worker that enables the install never caches anything by design, so an installed app always shows exactly what the server serves (ENCRYPTION.md, section 11).

Right after installing, check that JavaScript is enabled for the app: on some devices freshly installed web apps start with it off and the install dialog offers no switch (reported on a Google Pixel). The symptom is a dead login page - see Troubleshooting; long-press the icon > Settings > JavaScript fixes it.

4. Your files

The file explorer works like a desktop file manager, in the browser:

  • New file / New folder create entries in the current folder; a new

text file opens straight in the built-in editor (with a Markdown preview toggle and Save).

  • Upload file / Upload folder, or drag & drop onto the drop zone,

upload files or whole folder trees (empty subfolders included).

  • Show hidden toggles entries whose name starts with a dot; the choice

is remembered in your browser.

  • Click a file to preview it: images, video, audio, PDF, HTML and text

open in a lightbox; text files open in the editor.

  • Closing the editor with unsaved changes - or stepping to another file

with the gallery arrows - asks first, with Save as the focused default (Enter), Discard and Cancel. If the save fails the lightbox stays open and the status line carries the error, so the text is never closed over.

  • Selection checkboxes (Shift+click extends over a range) give you the

bulk bar: Download (the whole selection as one ZIP), Move to..., Copy to..., Share, Delete and Clear.

  • Every row also has a menu (Download, Share, Move, Copy, Rename, Delete).
  • Folder rows show their recursive size; the breadcrumb walks you down the

tree.

ZIP downloads are assembled per request and capped at 1 GiB uncompressed; take fewer items if the error tells you to.

Version history

Every content replacement - the editor's Save, a WebDAV PUT - keeps the replaced bytes as a restorable version, so a wrong save is never the end of a file. The row menu's Version history opens the file's history, newest first, with time and size per version:

  • Download fetches that version's exact bytes, ranges included (a

player can seek in a version like in the current file).

  • Restore exchanges: the chosen version becomes the file's content and

what was current becomes the newest version - a restore is itself undoable.

  • Delete removes one version together with its bytes.

A read-only share sees the history and can download versions; changing it needs write permission. Kept versions count against your quota, and the trash keeps a file's history until the file is purged. Two bounds in Settings ("Version history") keep the history in check: how many versions to keep per file, and an age in days - 0 disables either bound. A background sweep applies the age bound on the same cadence as the trash purge; the count bound is applied whenever a version is saved.

Office documents

If your instance runs an office engine (see INSTALL.md), office files - docx, xlsx, pptx, odt, ods, odp - open in a browser editor instead of staying inert: click the file (or Open in office editor in the row menu), edit, close. The save comes back through the same doors as any other write: it counts against the quota, shows up in the version history above, and is refused for encrypted files (the built-in editor handles those). Without an engine configured nothing changes - the rows keep behaving exactly as before.

5. Sharing

Share files or folders with other accounts of the same instance:

  1. Select one or more items and press Share.
  2. Pick the user from the dropdown.
  3. Tick the permissions to grant: Read, Write, Create,

Delete (a fifth box, Share, is reserved for re-sharing and has no effect yet).

  1. Press Share.

A share appears in the other person's root file tree, marked with your name; if the name is taken there, it gets a suffix (Projekte becomes Projekte (alice) 2). Everything they create inside a shared folder lands in *your* tree and counts against *your* quota.

To revoke, open the Share dialog for the item again and press Remove next to the person.

When encryption is on for both sides, the share also carries a key envelope sealed to the other person's public key - their key fingerprint is shown in the dialog so you can compare it out of band before trusting the exchange.

Public links

A public link hands a folder or a single file to anyone who has the URL - no account, no sign-in. It lives in its own Public link section of the Share dialog:

  1. Pick what visitors may do: Read - view and download, **Add -

upload only or Full - upload, download and delete**.

  1. Pick how the link expires: 30/90 days after last use (rolling, the

default), 30/90 days after creation (fixed) or Never.

  1. Optionally type a Label so you can tell your links apart later.
  2. Press Create link. The URL is shown once, with a Copy link

button - copy it now. The server keeps only a hash of the token and can never show the URL again.

Anyone opening the link sees a plain page with the folder's contents (folders one level at a time, downloads as attachments) - no sign-in, no referrers, no search-engine indexing. The link reaches exactly the item it was minted on and everything below it; nothing else in your account is exposed.

The section also lists every link you created: label, preset, deadline, last visit and download count, with Remove to revoke one. Revoking takes effect immediately - the URL answers *not found* from the next request on.

Things worth knowing:

  • Rolling vs fixed: a rolling link dies only after the chosen number

of days *without* a visit, and every visit pushes the deadline out to a full window again. A fixed link expires exactly N days after you created it, no matter how often it is opened. An expired link answers "gone" at first and disappears for good shortly after - it is never brought back by someone opening it again.

  • Add and Full are writeable inbox links: everyone with the URL can

put files into *your* tree (they count against *your* quota). An Add visitor gets the upload box and nothing else - they can neither list nor download what is inside, not even the file names. With Full they can also browse and delete inside the shared folder - deletions land in *your* trash, and the shared folder itself can never be deleted through its own link. Use Read when you only want to hand something out.

  • Plaintext only: an encrypted file or folder cannot be linked (the

section explains this on the spot), and encrypted files inside a linked folder stay invisible to visitors.

  • Group folders cannot be linked - membership is what grants access

there.

6. Group folders

A group folder belongs to a *group*, not to one person: a shared workspace with its own quota, managed membership, and the same tree for every member. Group folders wear the group's name as a badge in your root, so they stay tellable apart from a personal folder of the same name.

Creating one. An administrator creates the group itself (see User administration: name, quota in MiB, and the members with their roles - the creator becomes its first manager). You then create the group's root folder yourself with the New group folder... button at the top of your file list - offered in the root listing only, and only while you belong to a group. From then on every member sees that folder in their root and works the whole tree - upload, rename, move, trash - without any individual shares. A group folder cannot be shared out to a person: membership is what grants access.

Quota. The group's storage is its own budget, set by the administrator. Writes into a group folder count against the group, never against your personal quota; a full group refuses further uploads with 507 Insufficient Storage until the budget is raised or somebody frees space. Files in the trash keep counting until they are purged.

Keys. With encryption on, a manager hands out the folder keys: open the group root's row menu (the "..." column) and choose Distribute folder keys, then wrap and send to one member at a time. A member without a key sees the file names but cannot decrypt the content, and a member who has not set up file encryption cannot receive one yet (the button says so). Keys follow membership: removing a member removes their envelopes for that group as well.

Trash and deletion. Group files go to the trash like any other, and every member sees the group's trashed rows in their own trash view - restore and purge are open to any member. The group itself is deleted by an administrator once it is empty: no members, no folders.

7. Trash

Nothing is deleted immediately: Delete moves entries to your personal trash, where they can be Restored or Delete permanently. Empty trash clears everything at once.

A background sweep removes trashed entries for good after 30 days (FXCLOUD_TRASH_DAYS); the trash list shows each entry's deadline, and trashed content still counts against your quota while it sits there.

8. Quotas

Every account has a storage quota - 1 GiB by default, set per account by an administrator. What counts is everything *you own*: files you uploaded, copies you made, and content others shared *to you* counts against the original owner. Exceeding it yields a clear 507 Insufficient Storage error in the web UI and in WebDAV; your current usage is shown in Settings ("Storage: used of quota").

9. User administration

Administrators get a User administration entry in the menu behind their name in the top bar. The dialog opens on a Users tab; the Group folders tab beside it holds the group administration of section 6. On the Users tab they can:

  • activate / deactivate accounts (takes effect instantly: sessions and

WebDAV included; an administrator cannot deactivate themselves),

  • grant / revoke the administrator role (the last active administrator

can neither be deactivated nor demoted),

  • set the storage quota per account,
  • reset a password, which hands back a one-time generated temporary

password for the user's next sign-in.

Deactivated accounts can neither sign in nor use WebDAV and get a 403 with a hint to contact the administrator. Display name, theme and password are *not* on this list: every user changes those themselves in Settings.

The same switches are still available directly in the database (no restart required). On a systemd deployment the file is /home/fxcloud/data/fxcloud.db, in development ./data/fxcloud.db:

DB=/home/fxcloud/data/fxcloud.db

# overview
sqlite3 "$DB" "SELECT id, username, is_active, is_admin, quota_bytes FROM users ORDER BY id;"

# activate / deactivate (takes effect instantly: sessions + WebDAV included)
sqlite3 "$DB" "UPDATE users SET is_active = 1 WHERE username = 'max';"
sqlite3 "$DB" "UPDATE users SET is_active = 0 WHERE username = 'max';"

# administrator role
sqlite3 "$DB" "UPDATE users SET is_admin = 1 WHERE username = 'max';"

# quota (bytes; 1073741824 = 1 GiB, the default for every account)
sqlite3 "$DB" "UPDATE users SET quota_bytes = 2147483648 WHERE username = 'alice';"

10. Your account settings

The menu behind your name in the top bar opens Settings:

  • Account - username, member since, storage used of quota.
  • Display name - changeable by you, shown to other users.
  • Theme - Light or Dark.
  • Password - change it; the current password is asked first.
  • Passkeys - manage your sign-in devices (see below).

11. Encryption

fxcloud can encrypt files in your browser before they leave your device: the server stores ciphertext and a wrapped key, and can still see file names, sizes and sharing - those are what the storage service needs. The full design (threat model, key hierarchy, the DECISIONs) lives in ENCRYPTION.md; this is the user's view:

  • The badge in the top bar shows the state: Encrypt uploads (not set

up yet), Unencrypted, or Encrypted.

  • Turning it on, you choose between Use my fxcloud login password

(the default) and Choose a separate passphrase.

  • You are then shown a recovery key (64 hex digits). Save it: it is

the only way back into your files if the passphrase is forgotten.

  • The keys live in the current tab's memory only - a reload puts you back

to Unencrypted, and the unlock pane asks for the passphrase again.

  • With encryption on, uploads are encrypted, downloads and previews are

decrypted in the browser, and sharing carries the key envelope described above. WebDAV desktop clients do not encrypt: encrypted files are visible there as ciphertext and cannot be written through them.

Auto-unlock: open without the passphrase

Settings > Account > Auto-unlock is a switch that travels with your account: once a device has unlocked once, that browser keeps a random device key with your wrapped account key (localStorage, never your password) and every later opening - reload, new tab, password or passkey login - starts unlocked. The passphrase is asked exactly once more per device, at the one deliberate moment: you switching the badge from Unencrypted to Encrypted inside a live tab. A brand-new device asks once, then it too is silent. Off deletes the stored unlock and returns to the strict behaviour: keys live in the current tab only. The trade-off, openly: whoever can read this browser profile wholesale gets the keys of this account on this device - which is why the switch is off by default (ENCRYPTION.md 5.7, DECISION 7).

Encrypt existing files

Settings > Account > Encrypt existing files walks the whole tree in this browser, encrypts every plaintext file it finds and drops each file's old version history - that history *is* the plaintext. The dialog shows i of n, can be cancelled at any time, and resumes where it stopped: rerunning skips everything already encrypted. When the quota fills up it pauses with the quota message and offers Continue after freeing space. A folder's row menu has the same action for just that subtree (Encrypt folder now...).

Encryption zones

A folder's row menu (Encryption zone: on/off) marks it as a zone: new files and saves below it demand the passphrase even when the badge says Unencrypted, so that folder stays encrypted while the rest of the account stays WebDAV-compatible. Only the owner (or a group's manager) can change the flag, descendants inherit it automatically, and copying a folder does not carry it - set it again on the copy.

Recovery key: show it again or issue a new one

Settings > Account has a Recovery key section: enter the storage passphrase and Show recovery key displays it again (64 hex digits, with Download), or Issue a new one generates a fresh key behind a confirmation - the old key stops working the moment the new one is stored. A wrong passphrase never gets that far. Accounts set up before this version have no stored copy and answer "issue one here"; their first reissue enables showing for them too.

12. Passkeys

A passkey signs you in with a PIN or biometrics instead of a password. fxcloud uses username-first FIDO2/WebAuthn with ES256 and requires user verification (a PIN or biometric gesture, not just a touch).

Add one: open Settings, Passkeys, press Add passkey, give it a name (e.g. "phone", "security key") and confirm with your device. The list shows your devices with their last use; each can be Renamed or Removed. Removing the last one is allowed - your password keeps working, and a lost device can be cut off immediately.

Sign in: switch to the Passkey tab on the sign-in page, enter your username, and confirm with the device's PIN or biometrics. An unknown username and an account without passkeys get the same answer, so the dialog does not reveal who has an account.

Requirements:

  • A secure context: browsers only expose passkeys over HTTPS or on

localhost. Over plain HTTP on a LAN address the UI tells you the browser blocks them.

  • The passkey is bound to the origin and hostname it was created under.

If your instance is served under a URL, that URL must be announced to fxcloud with FXCLOUD_ORIGIN - the next section shows how, and what the error looks like when it is missing.

Inside a native Android app: the "this app doesn't support passkeys" wall

Signing in on the web works with every browser and password manager - plain WebAuthn, nothing below applies. Signing in from the Android app goes through the platform's Credential Manager instead, and that path has a trapdoor the whole industry has been tripping over since November 2025:

  1. The app asks the device's credential provider (Bitwarden against your

own Vaultwarden, Google Password Manager, ...) for a passkey.

  1. Before releasing it, the provider must prove the *app* is allowed to

use this domain's passkeys. Bitwarden's Android app does that through Google's Digital Asset Links API - the check Google's own credential-provider documentation recommends. It is a lookup about a *public* file: no key, no password, no passkey material ever leaves your password manager, self-hosted or not.

  1. That API fetches https://<host>/.well-known/assetlinks.json

without following redirects and in practice with the DNS-root form of the host (https://<host>.).

  1. Answer either request with a redirect or a 404 - a vhost that simply

does not know the dotted name is enough - and the provider refuses with a generic message:

> "Diese App unterstützt keine Passkeys" / "Passkeys are not > supported for this app"

Everything else can be perfect - file present, JSON valid, certificate fingerprints correct - the check still fails.

This is not your mistake and not fxcloud's. Revolut lived with exactly this error for months (bitwarden/android#6164, November 2025 to July 2026), Google's own tracker still carries the bug (issue 460172858), and Bitwarden shipped a workaround and reverted it again because strict matching is what the spec says. Nobody should have to explain a Google API quirk to their users - this section exists so you can forward it instead of writing it yourself.

Operators - the checklist that keeps every provider happy:

  • /.well-known/assetlinks.json answers directly with 200 and

Content-Type: application/json - no redirect anywhere on the https URL (the DAL API refuses to follow one).

  • The same URL answers with the trailing dot in the host:

https://your.domain./.well-known/assetlinks.json. With nginx one line in the same server block: server_name your.domain your.domain.; - in a proxied setup that is almost always the proxy in front of fxcloud, not fxcloud itself.

  • The file lists every certificate that can sign an installed build:

local debug key, release APK key, and under Play App Signing both Google's classic and the post-quantum key. One statement per fingerprint: some verifiers only read the first entry.

Users who landed here from the error: nothing on your phone can fix this - your instance's operator runs the checklist above. The web interface signs you in with the same passkey in the meantime. After the operator's fix, give Google's cached verdict a moment (ten minutes to a day) before retrying in the app.

On running without Google: the Bitwarden/Vaultwarden path sends Google only the public-file lookup described above - your keys stay on your own server. Providers that fetch the file themselves (Google Password Manager does) work even without the dotted host, but then the passkeys live in that provider's store. If your stance is "my data stays with me" - and if you are reading fxcloud, it is - fix the proxy line instead: one line, and everything else stays yours.

13. HTTPS behind a reverse proxy (worked example)

fxcloud speaks plain HTTP, so a reverse proxy terminates TLS in front of it. Passkeys are the reason this needs one extra setting: WebAuthn binds every passkey to the exact scheme://host[:port] it was created under, and the browser sends its Origin on every passkey request. fxcloud compares that header with the origin it derives from the forwarded scheme and Host - and, behind a proxy that rewrites Host or does not forward the scheme, the two disagree.

The symptom is this error, when adding or using a passkey:

bad request: Origin does not match this server's address - set
FXCLOUD_ORIGIN to the URL users open it under

The fix is one environment variable: tell fxcloud the URL users actually open it under. Worked example with nginx on cloud.example.com and fxcloud on the same host, port 8080:

1. fxcloud (systemd unit, or the shell for a quick test):

FXCLOUD_BIND=127.0.0.1 FXCLOUD_PORT=8080 \
FXCLOUD_SECURE_COOKIE=1 \
FXCLOUD_ORIGIN=https://cloud.example.com \
./fxcloud

In the provided unit file (deploy/fxcloud.service) the same two lines, commented, wait in the environment section:

# Enable when serving over HTTPS behind a TLS-terminating reverse proxy:
# Environment=FXCLOUD_SECURE_COOKIE=1
# The exact URL users open fxcloud under - required for passkeys when a
# reverse proxy rewrites Host or terminates TLS (e.g. https://cloud.example.com):
# Environment=FXCLOUD_ORIGIN=https://cloud.example.com

2. nginx terminates TLS and forwards to it:

server {
    listen 443 ssl;
    server_name cloud.example.com;

    client_max_body_size 10G;   # keep in sync with FXCLOUD_MAX_UPLOAD_MB

    location / {
        proxy_pass http://127.0.0.1:8080;
        proxy_set_header Host              $host;
        proxy_set_header X-Real-IP         $remote_addr;
        proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_request_buffering off;
        proxy_buffering off;
    }
}

3. Restart fxcloud (after changing the unit: sudo systemctl daemon-reload && sudo systemctl restart fxcloud).

Rules for the value of FXCLOUD_ORIGIN:

  • It must equal what the browser's address bar shows as origin: scheme,

host, and port if it is not the scheme's default (443 for https, 80 for http) - and no trailing slash, no path.

  • If users reach the instance under several names, passkeys work under

the one configured here; pick the canonical URL.

  • It only affects WebAuthn. Everything else keeps working with the proxy

headers from the nginx block above, and setting it is harmless when no proxy is involved.

Without FXCLOUD_ORIGIN, fxcloud derives the origin per request from X-Forwarded-Proto (or FXCLOUD_SECURE_COOKIE) plus Host, which is correct when the proxy passes both through unchanged - and wrong the moment it does not.

14. WebDAV

fxcloud speaks WebDAV at /dav/ with HTTP Basic auth (your fxcloud username + password; passkeys are web-only). The path after /dav/ is relative to your home folder:

rclone config    # type: webdav, url: https://your-host/dav/, user/pass
rclone lsd remote:

# Windows "Map network drive" / macOS Finder "Connect to Server" -> /dav/

Deactivated accounts get 403, quota violations 507. Encrypted files show up as ciphertext and cannot be written from a desktop client (see Encryption); the web UI is the way in and out for those.

15. Troubleshooting

"Diese App unterstützt keine Passkeys" / "Passkeys are not supported for this app" when signing in from the Android app: the device's credential provider could not verify the app against your domain's assetlinks file (Google's DAL API, redirects and trailing dots - section 12 has the full story and the operator checklist). Until it is fixed, the web interface signs you in with the same passkey.

"Origin does not match this server's address - set FXCLOUD_ORIGIN ..." when adding or using a passkey: the URL users open fxcloud under differs from what fxcloud derives from the proxy headers. Set FXCLOUD_ORIGIN as in section 13 and restart.

The passkey UI says the browser blocks passkeys: you are on plain HTTP (or an IP address) rather than HTTPS or localhost - browsers only expose passkeys in a secure context. Serve fxcloud over HTTPS.

"Account created. It has to be activated before you can sign in": expected for every account after the first - an administrator activates it in User administration.

"account is not activated yet - ask an administrator to activate it" at sign-in or over WebDAV: same cause, now on an existing account.

507 "storage quota exceeded: X of Y used": your quota is full - empty the trash (it keeps counting), delete files, or ask an administrator to raise the quota.

Encrypted files do not open: the storage passphrase is not unlocked in this tab (the keys live in tab memory only) - use the unlock pane; if the passphrase is forgotten, the recovery key from setup recovers it.

Sync client writes fail on encrypted files: desktop clients do not encrypt; WebDAV serves those files as ciphertext, read-only. Use the web UI for encrypted content.

Login page is dead: the Passkey / Create account tabs do not react, the page shows English although your browser is German, and submitting just brings the mask back without any error: JavaScript is switched off for fxcloud. On some devices this is the default for freshly installed web apps and the install dialog offers no switch (reported on a Google Pixel; a Samsung did not offer the setting at all) - the page script is what wires the tabs and intercepts the form, so without it the browser falls back to a plain reload. Fix: long-press the fxcloud icon, open Settings, enable JavaScript (or Chrome > Settings > Site settings > JavaScript), reopen the app. A different cause with a partial overlap: if the tabs DO react and the page is in your language but signing in still loops back to the mask, the session cookie is being dropped instead - check the address bar says https:// and clear the site's data in the browser settings.
